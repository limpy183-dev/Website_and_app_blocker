# 1. FocusFortress Warning & Alarm Functionality Report

## 1.1 Purpose

This report describes how to add custom warning, alarm, and popup functionality to the current FocusFortress app.

The current app is a Windows-only website and application blocker built with Python and PyQt6. It already supports block lists, website blocking, app blocking, schedules, Pomodoro cycles, allowances, locks, tray behavior, startup behavior, statistics, and anti-bypass controls.

The new functionality should **not replace the existing app** or turn it into a standalone timer alarm app. Instead, it should add a configurable **warning layer** that works with the app’s existing block system.

The goal is:

```txt
When a block, timer, schedule, Pomodoro phase, or allowance event happens,
FocusFortress can show a custom warning popup and optionally play a sound.
```

Example:

```txt
YouTube block becomes active:
    play scream.mp3
    show "GET OFF YOUTUBE"
    keep popup visible for 8 seconds
    fade away
```

# 3. Main Feature Direction

## 3.1 Correct Product Direction

The correct direction is:

```txt
Add custom warning behavior to FocusFortress blocks.
```

Not:

```txt
Build a separate custom timer/reminder app.
```

The warning system should answer questions like:

```txt
What should happen when this block activates?
What sound should play?
What warning message should appear?
How long should the warning stay visible?
Should the popup require dismissal?
Should the warning repeat or only fire once?
```

## 3.2 Example Use Case

```txt
Block name:
YouTube Limit

Blocked websites:
youtube.com
m.youtube.com

Schedule:
Every weekday, 18:00-21:00

Warning:
Message: "You said you were revising. Get off YouTube."
Sound: C:\Sounds\scream.mp3
Volume: 85%
Popup duration: 8 seconds
Fade out: enabled
Always on top: enabled
Dismiss mode: auto-close
```

When the schedule starts, FocusFortress blocks YouTube and shows the warning.

# 5. Warning Configuration

## 5.1 Per-Block Warning Settings

Each block should be able to have its own warning settings.

Recommended fields:

```txt
warning_enabled: true / false
warning_message: text
warning_sound_path: file path
warning_volume: 0-100
warning_popup_duration_seconds: number
warning_fade_enabled: true / false
warning_fade_seconds: number
warning_always_on_top: true / false
warning_dismiss_mode: auto_close / click_to_close / type_to_dismiss
```

## 5.2 Why Per-Block Settings Are Best

Per-block settings are the best fit because the app already organizes behavior around blocks.

Examples:

```txt
YouTube block:
    loud warning
    aggressive message
    short duration

Sleep block:
    calm sound
    gentle message
    longer duration

Study block:
    simple popup
    no sound
```

This avoids creating a separate timer system that duplicates what schedules, Pomodoro, and allowances already do.

# 6. Trigger Events

## 6.1 Block Activation Trigger

The most important trigger is:

```txt
When a block becomes active.
```

This includes:

```txt
User manually enables a block
A scheduled block starts
Pomodoro starts a work interval
Allowance runs out and block resumes
```

## 6.2 Pomodoro Trigger

Warnings should optionally trigger when Pomodoro changes phase.

Examples:

```txt
Work phase starts:
"Focus time. Distractions are blocked."

Break phase starts:
"Break started. You have 5 minutes."

Pomodoro ends:
"Cycle complete."
```

This should be optional because not every user wants popup warnings for every Pomodoro phase.

## 6.3 Allowance Trigger

Warnings should optionally trigger when daily allowance reaches zero.

Example:

```txt
Your YouTube allowance is finished.
The block is now active again.
```

This is a strong fit for the current app because allowances already exist.

## 6.4 Timer Lock Trigger

If a block has a timer lock, warnings could trigger when:

```txt
The locked block starts
The unlock timer finishes
The user tries to disable it early
```

For MVP, only block activation should be required. Timer-lock warnings can come later.

# 7. Warning Popup

## 7.1 Popup Requirements

The popup should support:

```txt
Custom warning text
Always-on-top mode
Custom duration
Fade-out animation
Manual close option
Large readable text
Dark app styling
```

The popup should match FocusFortress visually instead of looking like a default Windows message box.

## 7.2 Popup Modes

Recommended popup modes:

```txt
Compact alert
Centered warning
Full-screen warning
```

For MVP, only **centered warning** is needed.

## 7.3 Centered Warning Popup

Example:

```txt
+--------------------------------------+
|             FOCUS WARNING            |
|                                      |
|        GET OFF YOUTUBE BRO           |
|                                      |
|        [I understand]                |
+--------------------------------------+
```

Recommended behavior:

```txt
Appears above normal windows
Can auto-close after X seconds
Can fade away
Can be dismissed if allowed
Does not permanently trap the user
```

## 7.4 Full-Screen Popup

Full-screen popup should be later, not MVP.

It is useful for strict warnings, but it has more risk:

```txt
Could annoy users too much
Could feel malware-like if not dismissible
May not appear above exclusive full-screen games
Needs careful escape behavior
```

# 9. Dismiss Behavior

## 9.1 Auto-Close

Default behavior should be:

```txt
Show popup
Play sound
Wait for configured duration
Fade out
Close popup
Stop sound
```

This is simple and safe.

## 9.2 Click To Close

Optional behavior:

```txt
Popup stays until user clicks "I understand".
```

This is useful for warnings that should not be missed.

## 9.3 Delayed Close Button

Strict mode could use:

```txt
Close button appears after 10 seconds.
```

This is annoying enough to work, but still safe.

## 9.4 Type To Dismiss

Later strict mode option:

```txt
To close, type:
"I will stop wasting time"
```

This should be optional and never used by default.

## 9.5 What Not To Do

Avoid:

```txt
Impossible-to-close popups
Blocking Task Manager just for warnings
Infinite sound with no stop
Preventing app exit outside existing lock rules
Fake system dialogs
Scary behavior that resembles malware
```

FocusFortress can be strict, but it should remain user-controlled and understandable.

# 11. Data Model Changes

## 11.1 Add WarningConfig

A clean design would add a new config model:

```python
@dataclass
class WarningConfig:
    enabled: bool = False
    message: str = ""
    sound_path: str = ""
    volume: int = 80
    popup_duration_seconds: int = 8
    fade_enabled: bool = True
    fade_seconds: int = 2
    always_on_top: bool = True
    dismiss_mode: str = "auto_close"
```

## 11.2 Add WarningConfig To BlockList

Each block should contain:

```python
warning: WarningConfig = field(default_factory=WarningConfig)
```

This keeps warning behavior attached to the block it belongs to.

## 11.3 Backward Compatibility

Existing config files should continue to load.

That means `AppConfig.from_dict()` needs to handle old block configs that do not have a warning field.

Expected behavior:

```txt
Old config loads normally
Missing warning field gets default WarningConfig
No existing blocks break
```

# 12. Engine Behavior

## 12.1 Detect Block Activation

The engine already checks which blocks are effective/enabled.

The warning system needs to know when a block changes from:

```txt
inactive -> active
```

Then it can trigger the warning once.

## 12.2 Avoid Repeated Warnings

The engine runs repeatedly, so it must not show the warning every tick.

It needs state like:

```txt
previous_active_blocks
current_active_blocks
newly_active_blocks = current - previous
```

Warnings should only fire for `newly_active_blocks`.

## 12.3 UI Thread Safety

The engine runs background work.

PyQt UI popups should be shown from the Qt main thread.

Recommended design:

```txt
Engine detects event
Engine emits/calls warning event
Main window receives event
Main window shows popup
```

Do not directly create PyQt windows from the engine thread.

# 13. Warning Manager

## 13.1 New Warning Manager Component

A small warning manager should handle warning playback and popup display.

Responsibilities:

```txt
Receive warning request
Validate warning config
Play sound
Show popup
Stop sound when popup closes
Prevent duplicate popups
Handle test warning from UI
```

## 13.2 Suggested Files

Possible new files:

```txt
focusfortress/warnings.py
focusfortress/ui/warning_popup.py
```

Or:

```txt
focusfortress/ui/warnings.py
```

Keep the logic separated so the engine does not become responsible for popup styling or audio details.

# 16. Strict Mode

## 16.1 Purpose

Strict mode makes the warning harder to ignore.

It should be annoying, but not dangerous.

## 16.2 Safe Strict Mode Options

Good options:

```txt
Close button appears after X seconds
Type phrase to dismiss
Click and hold to dismiss
Require "I understand" click
Repeat warning every X minutes while block stays active
```

## 16.3 Unsafe Strict Mode Options

Avoid:

```txt
Cannot close popup
Cannot stop sound
Blocks Task Manager just because warning is active
Hides from user
Relaunches popup instantly forever
Prevents normal Windows use outside configured block rules
```

Strict mode should always be clear and configurable.

# 18. Limitations

## 18.1 Full-Screen Games

Some full-screen games may appear above the popup.

This is especially true for exclusive full-screen games.

Expected behavior:

```txt
Sound should still play
Popup may not appear above every game
Borderless fullscreen is more likely to show the popup correctly
```

The app should not overcomplicate this in the first version.

## 18.2 Audio File Problems

Possible issues:

```txt
File missing
Unsupported format
File moved after being selected
Audio device unavailable
Volume too low
```

The app should fail safely:

```txt
Show popup anyway
Do not crash
Show a small error if testing sound fails
```

## 18.3 Multiple Warnings At Once

If several blocks activate at the same time, the app should avoid popup spam.

Recommended behavior:

```txt
Show one combined warning
Or queue warnings
Or only show the highest-priority warning
```

For MVP, the simplest option is:

```txt
If multiple blocks activate together, show the first warning only.
```

# 21. Final Recommendation

The feature is worth adding, but the original report should be changed from:

```txt
A custom timer / focus alarm app
```

to:

```txt
A custom warning and alarm system inside FocusFortress.
```

The strongest first version is:

```txt
Per-block warning settings
Custom message
Custom sound
Volume
Always-on-top popup
Duration
Fade-out
Trigger when a block becomes active
```

That fits the current app, avoids unnecessary rewrites, and gives the user the main functionality immediately.
